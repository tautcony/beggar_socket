## 一、优先保留的客户端改进

| 优先级 | 改进 | 客户端实施位置 | 验收要点 |
|---|---|---|---|
| P1 | 按真实 CFI 地址计算物理扇区交集 | `utils/sector-utils.ts`、GBA/MBC5 adapters | 非零 base、异构 boot sector、跨扇区范围得到正确擦除地址 |
| P1 | 在擦除前验证写入区间和输入长度 | adapters、burner application | 输入不足、越过容量、非法地址/粒度请求在任何 erase/program 前失败 |
| P1 | 按实际发送长度计数，完成量不足不得报成功 | GBA/MBC5 `writeROM` | 4B 输入配 8B size 的 API 反例不能少写成功；空 chunk 不能进入成功出口 |
| P1 | 写入与完整校验使用同一份补齐镜像 | `CartBurner.vue`、adapters | 写入的 `0xFF` 补齐区也受完整校验覆盖；部分校验明确范围 |
| P1 | 读取/写入/校验共享 bank 分块约束 | GBA/MBC5 adapters | GBA 32MiB、GB 16KiB 窗口及尾块不被单次请求跨越 |
| P1 | 协议封装校验帧长、长度字段和地址单位 | `protocol/beggar_socket/`、settings | 不发送超限/截断长度、非法奇数 ROM payload；F5 word 地址与 F4/F6 byte 地址明确 |
| P1 | 写入能力与 CFI command set、MBC 实现匹配 | CFI parser、adapters、UI | 识别到容量不等于可写；未实现路径在破坏性命令前拒绝 |
| P2 | 整扇区重放与部分写入策略一致 | adapters、应用层 | 失败后重擦/重放使用真实扇区；输入范围外数据按明确策略处理 |
| P2 | 取消状态与实际请求结束时机一致 | burner session、UI、transport 调用方 | 在途命令未结束时显示取消中，结束前不启动下一操作 |
| P2 | 分别量测擦除、传输、重试与总耗时 | progress、transport、adapter 日志 | 基于有效完成量报告吞吐，不把仿真速度当实物速度 |

### 1. 物理扇区计算

`calcSectorUsage()` 当前从 `baseAddress` 重新顺次铺设 CFI 区块，没有与区块本来的绝对 `startAddress/endAddress` 求交（`utils/sector-utils.ts:4`）。

例如真实扇区为64KiB，从 `0x8000` 写入64KiB，实际覆盖两个物理扇区，当前算法可能只生成一个从 `0x8000` 开始的假扇区。异构 boot-sector 布局下，非零且对齐的 UI 基址也可能错误复用芯片首部几何。

客户端即可修正：按真实 CFI 区域枚举与 `[base, base+size)` 相交的物理扇区，校验容量后再发擦除。部分扇区写入需要明确策略：现阶段可先拒绝无法完整覆盖的请求；若产品需要任意局部更新，再用现有读取、擦除和编程命令实现读出、合并和整扇区回写。

### 2. 写入范围与完成量

GBA/MBC5 adapters 以 `options.size` 计划传输，但文件切片可能更短，进度仍按计划 chunk 长度增加。例如4B输入、8B size、足够大的页，实际只发4B却可能报成功（`gba-adapter.ts:402,521,552`；MBC5 有对应逻辑）。当前 UI 会先补齐短文件，因此该例主要是 adapter/use-case 输入契约缺口。

在首次擦除前验证有限整数、非空、输入覆盖范围、`base+size<=deviceSize` 和操作粒度；循环只累计实际完成量。允许写文件前缀时明确约定该范围，不能把输入不足作为正常完成。

### 3. 完整校验与 bank 边界

UI 写入使用补齐镜像（`CartBurner.vue:527`），校验使用原始文件（`:653`），verify 又取配置/容量/文件长度的最小值（`gba-adapter.ts:850`）。完整校验应复用写入镜像；允许前缀校验时，结果和日志需要说明实际区间。

GBA write 已限制 bank 剩余窗口，verify 尚未使用同样限制（`gba-adapter.ts:512,908`）。默认4096B页通常对齐，但页大小1000只告警、不拒绝；基址28MiB、范围跨32MiB即可触发跨 bank 的读取。客户端应统一按页、剩余总量和 bank 剩余窗口取最小值。

## 二、保留为可选项的 RC31 客户端适配

这些项目使用 RC31 已有命令，不要求修改本仓库固件；也不表示当前客户端已完成互通验证。

| 可选项 | 客户端需要完成的工作 | 前提 |
|---|---|---|
| 设备发现与 profile | Web/Tauri 筛选覆盖 `0483:5740`；明确选择协议和能力，避免默认标成 stm | PID 只能作为候选识别信息，不能代表全部能力已确认 |
| FlashGBX 会话 | 在现有 gateway/transport 上实现独立协议封装，正确初始化、解析结果和重连 | legacy 与 FlashGBX 同号命令不能混发；识别和会话必须验证 |
| C1 流式读取 | 管理请求长度、bank、接收总量和失败后的会话收尾 | 使用 RC31 已有 C1；不假定 legacy F6 自动流式加速 |
| D5 CRC32 校验 | 按相同区间计算主机 CRC；不一致时读回定位 | 确认 CRC 参数、地址/长度、范围和 bank 语义；保留逐字节校验 |
| CA RTC 读取 | 在 RC31 profile 下调用已有批量读取，解析结果 | 只确认 RC31 的读取入口；当前主机已有的 RTC 设置仍走既有路径 |

RC31 legacy 自动识别会把某些帧长低字节解释成 FlashGBX 命令。例如 F4 数据1000B，总长1011=`0x03F3`，首字节 `F3` 会被作为另一个协议的关电命令；64B数据的F4总长 `0x004B`，长度头单独分包还可能被当 probe 消费。此处仅保留为客户端兼容约束：不能把“添加 PID”视为完成支持，不能假定任意页大小和尾块都可发送。客户端适配须验证完整会话及全部实际帧形态，无法可靠互通的路径暂不启用。没有抓到故障分包、也未在实机重放上述源码反例。

## 三、可直接借鉴的实现原则

- 一个读写操作先确定镜像、范围、物理扇区和分块，再进入执行；写入与校验使用相同定义。
- 保留有限重试及当前扇区重放，恢复依据必须是真实物理地址；用带存储副作用的 mock 检查读回结果。
- 保留现有逐命令串行访问。同一设备不要并发发命令来追求吞吐。
- legacy 两字节 CRC 尾仍按现有约定发送；`PayloadBuilder.build(false)` 已包含尾部，不需要补一个重复尾部或单方面强制 CRC。
- 支持表依据已实现的协议路径与卡型，而非枚举值、厂商 ID 或“透传理论上可做”。

## 四、实施与验证顺序

1. 修正扇区计算和写前范围契约，覆盖非零 base、异构区块及少写成功反例。
2. 统一写入/校验镜像、完成量和 bank 分块，覆盖补齐区错误、设备末尾和跨窗口请求。
3. 加入协议封装边界、能力检查和重试/取消回归，保持现有连接与 legacy 路径兼容。
4. 按需求适配 RC31 已有协议，先验证发现、会话和只读操作，再评估 CRC 与 RTC 读取的收益。
