# web-client 可利用的卡带和协议能力

范围：保留客户端能在现有协议上完成的改进，以及对 RC31 已有命令的可选适配。设备端内核、USB、总线、电气和工具链的移植方案不在本报告内。

## 1. 当前客户端的职责和可用基础

| 功能 | 当前实现 | 可保留的改进 |
|---|---|---|
| CFI/ID | `gba-adapter.ts:1457`、`cartridge-adapter.ts:470` 透传查询并由主机解析 | 解析并校验操作能力；容量、扇区和命令集不能相互替代 |
| 扇区擦除 | 主机发送已有解锁序列并轮询，安排扇区与重试 | 按真实CFI地址计算交集；先验证全部范围，再开始擦除 |
| ROM编程 | F4/FC带地址、bufferSize和数据；adapter负责切块 | 确认数据长度、范围和粒度，统一页/扇区/bank约束，按实际完成量计数 |
| ROM校验 | F6/FB读回后逐字节比较 | 复用写入镜像，覆盖补齐区域；结果明确已验证范围和首错地址 |
| GBA存档 | SRAM/Flash/FRAM按profile选择；另有batteryless工作流 | 操作能力检查、范围约束、读取失败和实际完成量验证 |
| RTC | GBA RTC主机F5/F6位操作；MBC3 RTC主机寄存器读写 | 保留既有能力；RC31可选择已有CA批量读，避免改动原设备要求 |
| MBC | MBC3/MBC5 bank逻辑已实现；MBC1/MBC2部分路径显式未实现 | UI、操作入口和支持表与实际路径一致，避免擦除后才发现未支持 |

当前流程可以保留：burner application → cartridge adapter → protocol → transport。上述输入检查、几何修正和数据一致性不需要新的设备命令。

## 2. 地址与报文契约

`web-client/src/protocol/beggar_socket/protocol.ts:147,154,168` 分别封装 F4/F5/F6：

| 命令 | 地址单位 | 客户端注意事项 |
|---|---|---|
| F4 ROM program | byte | 地址/数据应符合16-bit ROM访问粒度；检查固定开销与实际payload长度 |
| F5 ROM direct write | word | 不与F4/F6共用未经区分的地址转换；控制序列调用只转换一次 |
| F6 ROM read | byte | 按目标profile上限与bank窗口切块；读回长度必须符合请求 |
| GB/GBC raw read/write | byte | 主机负责MBC窗口与bank状态，跨窗口重新选择bank |

`rom_erase_sector()` 将byte扇区地址转换成word地址再通过F5发出，见 `protocol.ts:122`。重构协议封装时应测试实际发送字节，不因变量名相同而统一单位。

`PayloadBuilder.build(false)` 已返回两个尾部占位字节（`payload-builder.ts:81`）。当前legacy模式不校验此CRC；保持线级兼容即可，不单方面改变校验约定。应在客户端检查长度字段可表示范围、profile命令上限、非空payload和对齐，防止调用方构造超限/截断请求。

## 3. CFI 与写入能力

`cfi-parser.ts:225` 当前把 `isIntel=false`，没有完成primary command set ID解析。CFI查询成功只能说明获得了几何等信息，不能证明当前选用的编程路径支持该命令集。

保留的客户端改进：

1. 解析真实command set信息，并与所选协议/已实现方法匹配。
2. 在任何擦除前拒绝未支持的写入路径；错误信息说明该卡操作能力，而非仅显示“连接成功”。
3. 保留已经明确实现的型号特例，不能仅按厂商ID一刀切；例如MBC5有 `0x89` 的bufferSize调整（`mbc5-adapter.ts:670`），需要以对应操作路径和目标卡证据判断。
4. CFI扇区地址和设备容量经过一致性检查后才生成执行计划。

此处保留能力识别与拒绝策略，不将新增Intel或其他设备编程算法列为当前实施任务。

## 4. 现有 RTC、MBC 和存档能力

- `services/rtc/gba-rtc.ts:20` 用F5 word地址操作GPIO、用F6 byte地址读回，已有RTC读取和设置流程。`mbc3-rtc.ts:17` 使用GBC寄存器读写。不要将其误报成客户端功能缺失。
- `mbc5-adapter.ts:253` 的具体bank实现决定支持范围：MBC3/MBC5有实现，MBC1 ROM/RAM与MBC2 ROM部分路径抛出未实现。UI枚举与实际操作能力需要一致。
- `gba-adapter.ts:1652` 起有GBA batteryless区域搜索、擦除、编程和读回工作流。它应复用正确的物理扇区、区间和校验契约。
- RC31没有被本次分析证实具有与该batteryless工作流等价的端到端支持，不能据特殊算法列表替换现有流程。

## 5. RC31 现有协议可提供的客户端扩展

附件源码路径以下以 `sdcc_flashgbx_rc31/src/` 为根。这些内容是可选协议适配依据，不代表当前客户端已支持或已实测。

| 能力 | 既有入口 | web-client 需要实现的部分 | 验证 |
|---|---|---|---|
| 流式ROM读 | C1，`flashgbx.c:373` | 独立会话、模式/范围设置、总量接收、bank分段和错误收尾 | 与同范围legacy读回一致，跨窗口不丢/重复数据 |
| ROM CRC32 | D5，`flashgbx.c:771,1074` | 明确CRC参数和范围，计算主机结果，解析比较；失败后读回定位 | golden vectors、错位/长度错误注入、与完整读回交叉验证 |
| GBA RTC批量读 | CA，`flashgbx.c:1030` | 在已确认profile选择该入口并解析结果 | 与现有主机读取结果比较；不据此宣称有CA写RTC支持 |

legacy F6仍走普通读取；切换设备不会让现有F6客户端自动得到C1收益。legacy与FlashGBX还有同号命令不同义的情况，如FlashGBX F4是供电查询，不是legacy ROM编程。需要独立协议封装并正确选择会话，不能把字节命令直接混入现有legacy调用。

RC31的EEPROM、MBC7和特殊卡方法虽然在源码中存在，但引入完整客户端工作流的范围较大、实机证据不足，本轮不列为优先优化待办。

## 6. 客户端适配的已知限制

RC31通过首字节识别FlashGBX，而legacy首字节是帧长低字节（附件 `uart.c:349`、`flashgbx.c:262`）。F4数据1000B时帧长1011=`0x03F3`，会被误分流到FlashGBX F3关电；F4数据64B时帧长 `0x004B`，长度头单独成包可能被当probe消费。

客户端接入需验证模式、实际帧长度、尾块和重连；默认4096B页的4107B F4帧不撞上述首字节，不能据此推断所有帧都可用。无法证明可靠互通的路径暂不启用。此处保留兼容条件，不提出修改设备分派逻辑的任务。

## 7. 性能评估

先记录现有legacy路径的总耗时、擦除耗时、有效数据量、请求数、ACK等待和重试次数，再评估RC31已有C1/D5/CA适配是否值得实施。同一设备上继续串行化命令，避免并发破坏bank/协议状态。

32MiB按4KiB读取需8192次请求；若每次额外固定开销为1ms，累计约8.2秒。这是估算而非实测结果。可优化的主机工作包括减少无必要的重复读取/初始化、按已有协议边界选择分块、合理更新进度，以及使用已确认的批量读取入口。不能通过增大payload或删除既有settle等待来假定提速，调整应有同板同卡前后对照。

附件模型集成与震感写入记录没有证明ROM/save互通或实际读取吞吐；现有客户端测试也不能替代该项测量。
