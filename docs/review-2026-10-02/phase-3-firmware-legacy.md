# Phase 3：固件边界、设备状态与旧版 C# 客户端

审查日期：2026-10-02。基线：GitHub 最新同步 HEAD `756179a`；不涉及 stash。只读审查源代码，唯一新增内容为本报告。未连接卡带或烧写设备，未执行破坏性硬件命令，也未宣称硬件验证通过。

## 覆盖与结论

重点覆盖 STM32 `Core/Src/uart.c`、`cart_adapter.c`、CDC 接收/发送实现；STC 活跃 Keil 工程实际引用的 `src/uart.c`、`usb.c`、控制线回调、板级初始化；旧 C# 的协议编码/串口接收、任务入口、取消及构建配置。Keil 工程明确引用 `stc/src/uart.c` 和 `cart_adapter.c`（`stc/stc_usb_ser.uvproj:380`、`:385`），旁路的 `uartstm.c`、`uartstc.c` 和时钟版本文件不当作当前运行逻辑。

本 phase 确认 7 项缺陷：P0 × 1，P1 × 5，P2 × 1；另外列出 3 类风险/验证缺口。最大问题是缺少协议帧验证和操作结果模型，改善抽象前应先固定有效帧与失败路径的行为。

## 已确认缺陷

### FW-01 / P0：STM32 接收边界没有约束命令语义，导致内存越界或异常卡带写入

- 位置：`mcu/chis_flash_burner/Core/Src/uart.c:160`、`:180`、`:506`、`:550`、`:580`、`:593`。
- 证据：接收函数只检查 5500 字节输入缓冲容量；分派函数只检查收到至少 3 字节且接收量达到声明长度，没有 opcode 对应最小长度、读取上限和对齐校验。RAM 写长度为无符号 `cmdSize - 9`；RAM 读把未约束的 `readSize` 直接写入只有 5498 字节的响应 payload。
- 触发：5 字节帧 `05 00 F7 00 00` 会产生 65532 字节的写长度并从命令缓冲之外读取数据，向卡带总线写入；合法长度 11 的 F8 帧若声明读取 5500 字节，则越过响应数组末尾。相同模式覆盖其他 RAM/GBC 读写路径。
- 影响：损坏固件内存、死机或向卡带写入非预期数据。即使上位机平时遵守 README，也不能由此保证分片、取消后残留或第三方客户端的输入安全。
- 修复：执行总线访问前按 opcode 校验完整固定头、总长、payload 长、读上限和字对齐；保留目前合法命令的线格式及 CRC 占位。非法输入不产生总线副作用。
- 验收：主机模拟总线记录，覆盖长度 0/1/2/3/4、低于最小长度、5500/5501、读取 5498/5499/65535、奇数 GBA 字节长度；所有拒绝帧总线访问次数为 0，合法最大协议帧行为与基线一致。

### FW-02 / P1：STM32 轮询超时被当作完成，仍向客户端返回成功

- 位置：`mcu/chis_flash_burner/Core/Src/uart.c:274`、`:288`、`:293`、`:303`、`:402`、`:405`、`:447`、`:493`、`:624`、`:629`。
- 证据：轮询函数为 `void`，达到 10000 ms 后直接退出；调用者没有区分完成和超时，并最终发送 `0xAA`。RAM Flash 编程还继续后续字节。
- 触发：卡带不存在、不支持该编程方式或 Flash 长时间未完成。
- 影响：返回成功但擦除/编程未完成，批量写入继续推进，用户误以为数据可靠。
- 修复：返回 `done/timeout/cancelled` 结果，第一处失败立即停止后续总线写操作，复位状态。已有 README 明确允许非 `0xAA` 表示失败的命令可保持一字节失败响应；不可擅自扩展旧客户端读取数据响应的长度。
- 验收：模拟硬件永远返回 busy，超时后不再写下一块且不发成功 ACK；正常、超时、DTR 取消三条路径各自验证。

### FW-03 / P1：GBA 编程 bufferWriteBytes=1 使循环无法前进并越界取值

- 位置：`mcu/chis_flash_burner/Core/Src/uart.c:429`、`:457`、`:458`、`:472`、`:482`、`:488`。
- 证据：非零缓冲大小进入批量分支；值 1 经 `/2` 变为 0，`writeLen` 为 0，`writtenCount` 永不增长，最后完成值通过 `dataBuf + writtenCount + writeLen - 1` 在数据首地址之前读取。
- 触发：有至少一个字的数据且缓冲大小字段为 1 的 F4 命令。
- 影响：循环重复发无效 Flash 命令，不能完成正常任务。
- 修复：GBA buffer 大小只接受 0 或有效的偶数并限制设备允许上限；确保每次编程分支写入长度大于 0。不能单靠全帧长度校验消除这一缺陷。
- 验收：buffer=0/1/2/奇数/最大值分别验证；非法值无总线副作用，有效分支单步推进数量大于 0。

### FW-04 / P1：STC 短包头和未知命令无法释放 OUT 端点

- 位置：`stc/src/uart.c:129`、`:134`、`:139`、`:201`、`:285`。
- 证据：接收量不超过 2 时不会调用 `endpointClear()`；主循环只在超过 3 时处理命令。未知 opcode 的 default 只 break，既不清指针也不清端点。
- 触发：长度字段分成 1 或 2 字节的首个 USB OUT 包，或完整未知命令（包括该固件当前未启用的 F3/E7/E8）。
- 影响：后续 OUT 包不能被正常接收或任务反复遇到相同命令，通常必须 DTR/RTS 复位。
- 修复：包头不足时释放端点继续接收；完整未知帧进入统一拒绝/清理分支。维护 STC 与 STM32 能力差异，不将注释掉的命令直接开放。
- 验收：每条有效命令按首片 1/2/3/4/64 字节分片重放；未知命令后无需重新插拔即可执行 ROM ID 查询；记录端点状态。

### FW-05 / P1：STC 完整帧等待和 USB 发送等待缺少退出条件

- 位置：`stc/src/uart.c:150`、`:157`、`:169`、`:296`、`:325`、`:614`、`:717`、`:1192`；复位路径 `:87`、`:96`。
- 证据：多处 `while(cmdBuf_i_wr < packSize)` 不检查 `cmdEnd`。控制线复位把指针置零，不能解除等待。数据发送永久等待 `ep1Busy`，ACK 在 USB 中断关闭时等待 FIFO 空；硬件完成轮询只有复位条件，没有时限。
- 触发：半帧中断、主机停止消费 IN 数据或卡带未完成操作。特别是已进入等待完整帧的函数后 DTR 复位，指针归零且仍小于原长度。
- 影响：主循环无法恢复下一条正常任务；客户端取消未必能让设备恢复。
- 修复：为接收、发送、硬件执行分别提供截止时间与取消出口，统一清理 GPIO/端点/帧状态；USB 中断屏蔽区域只覆盖必要寄存器操作，不能覆盖无界等待。
- 验收：在每个帧分片边界停止发送，再发 DTR，设备在规定时间恢复；主机停止读响应、拔插 USB、硬件 busy 均能退出；在真实 STC 板上检查时序与 IRQ 行为。

### FW-06 / P1：旧 C# 串口响应无截止时间，发送失败后仍永久等响应

- 位置：`client/ChisFlashBurner/cart_adapter.cs:65`、`:70`、`:80`、`:118`、`:138`、`:142`；`client/ChisFlashBurner/utility.cs:64`；取消 `client/ChisFlashBurner/Form1.cs:723`。
- 证据：响应轮询不设时限且忙等 `BytesToRead`，开串口时没有设置读写超时。发送方法吞异常且返回 void，调用者继续接收。即使增加 SerialPort.ReadTimeout，也不能覆盖尚未调用 Read 的 BytesToRead 循环。
- 触发：设备无响应、固件卡死、发送失败或仅返回响应前缀。
- 影响：工作线程永久占用 CPU，UI 状态保持忙；关闭串口时 BytesToRead 异常位于局部 try 外。
- 修复：抽出具有 deadline、取消与错误结果的串口事务；发送失败直接传播，接收以实际读取量推进；取消先通知固件复位并等待工作线程退出，再关闭串口。替代 Thread.Abort 的过程与 UI 线程更新一起完成。
- 验收：假的串口分别返回无数据、部分响应、发送异常、断连，事务均在截止时间结束；取消后能启动下一个任务，GUI 保持可操作。

### FW-07 / P2：旧 C# 接收忽略实际读取字节数

- 位置：`client/ChisFlashBurner/cart_adapter.cs:91`、`:95`。
- 证据：`SerialPort.Read` 返回值被忽略，计数直接增加请求量。读取不足请求量时将未填充部分视为已接收；CRC 又被禁用，无法检测数据错误。
- 触发：串口实际读取不足请求量（特别是流重置、缓冲变化等条件）。
- 影响：错误完成响应并可能把零字节写入 dump/校验数据。此处是 API 使用缺陷；在当前单读线程、健康连接时的发生频率尚未测量。
- 修复：使用 Read 返回数量推进并处理零返回；与 FW-06 同批处理。
- 验收：模拟连续短读 1、2、3 字节，拼接输出与输入精确相同，不提前完成。

## 高风险假设与残留疑点（不算已确认运行故障）

1. **ISR 与主循环共享变量的可见性和原子性。** STM32 `uart.c:49` 的 cmdBuf_p 没有 volatile；STC `uart.c:45`、`:52` 和 `usb.c:34` 的共享状态也无 volatile，16 位计数在 8 位平台上多处通过临时禁 USB 中断读取但其他读取没有同等保护。优化可能改变等待或复位行为，需要检查实际编译器输出与硬件复现。修复不能仅“全部加 volatile”：应规定状态所有权、IRQ 临界区和快照。
2. **STM32 发送生命周期。** `uart.c:147` 使用栈上 ACK 变量后异步发送；CDC `usbd_cdc_if.c:299`、`usbd_cdc.c:836` 保存地址。当前 STM32 USB PMA 底层可能在调用中同步复制单字节，因此不能仅凭存储指针断定 ACK 已损坏。响应共享数组还可能被 DTR 回调 `uart.c:106` 清零，发送期间的复位行为需验证。应统一由传输层拥有静态/持久缓冲，完成或取消后才释放/复用，并处理 USB 未配置状态。
3. **STC 流式写入的取消与计数一致性。** `uart.c:766` 的 RAM Flash 消费游标比 dataBuf 多 2 字节；最后两个 CRC 字节偶然填补差额，健康全帧不直接证明数据错写，但流式可用长度意义已不一致。包括零 payload 的 do-while、奇数字节 GBA 写入 `:579` 不能推进在内，应采用同一个“有效 payload 已接收/已消费”不变量并增加边界验证。

## 抽象与兼容改进方案

| 批次 | 工作 | 兼容边界 | 验收与回退 |
|---|---|---|---|
| A：建立基线 | 建立 opcode/帧长度/字段偏移/地址单位/ACK/能力矩阵；记录现有合法帧与期望响应 | 小端、2 字节 CRC 占位、0xAA、单请求事务、STM32/STC 差异均保持 | C# 与 Web 客户端编码的 golden vectors；设备只读 ID/ROM/存档快照；保存旧固件与 hash |
| B：固件入口修复 | FW-01/03/04，独立纯 C 校验和小端字段解码；先校验后产生总线副作用 | 不引入新协议版本，不突然启用 CRC，不开放未支持命令 | 主机 mock、恶意长度/分片矩阵；STM32 Debug/Release 均构建；STC C51 编译与板上分片重放 |
| C：状态恢复与结果 | FW-02/05，将等待结果和取消/USB 断连传到统一结束流程 | 成功线格式不变；失败 ACK 只用于旧客户端已支持的命令 | 计时、断连、DTR、设备 busy；取消后新事务无旧响应；正常读写性能与基线比较 |
| D：旧客户端事务封装 | FW-06/07，协议 codec、ITransport/SerialPortTransport、事务、UI 分离 | 先保留 .NET Framework 4.8 与现有功能入口 | 假串口失败路径；UI 取消、任务退出、资源释放；无需硬件验证纯编码 |
| E：减少重复实现 | 共用协议描述/golden vectors，平台分别保留总线与 USB 后端；按 capability 决定可执行命令 | GBA 字地址与字节地址明确区别；STC 时钟、NOP、GPIO 时序不抽成泛化动态层 | 对每个移出的函数核对总线轨迹；板上读/写/verify、RTC、FRAM、MBC bank 测试后再移除旧入口 |

不建议一次合并 STM32 与 STC 的整个 uart.c，也不建议先引入大型通用命令框架。STC 流式消费与 STM32 全帧执行、C51 内存模型、GPIO 时序是实质差异。可以共享可移植的协议契约、验证器行为及测试用例，让命令执行与平台传输各自保持小而明确的边界。

旧 C# 的 partial Form1 同时持有 UI、端口、codec 和任务（`Form1.cs:23`、`cart_adapter.cs:14`），并关闭跨线程 UI 检查（`Form1.cs:44`）。先抽可测试的事务及结果类型，最后才移动业务 mission；不把所有任务一次改为 async 来扩大回归面。

## 测试与覆盖限制

- 仓库 STM32 workflow 目前是 Debug/Release 构建及产物上传（`.github/workflows/build-mcu.yml:20`），不足以证明帧安全、轮询结果或电气时序正确。STC Keil 与旧 C# 构建/行为测试未在现有 workflow 见到。
- 本次静态追踪了入口到总线函数与响应调用，但未逐个验证卡带芯片指令集、所有 mission 算法、RTC 位序、板级原理图或第三方 HAL 全部实现。未运行固件构建/旧 C# 构建，不能据此判定当前产物可编译或不能编译。
- 无硬件可先完成：纯帧校验/解码的主机测试、总线 mock、fake clock 超时、取消事件、客户端串口短读与 golden vectors。必须实机完成：USB FIFO/IRQ 复位、GPIO/NOP 时序、所有支持芯片擦写与读回校验、电源/PHI 行为。
- 对写入功能，验收应使用可恢复的测试卡带与固定数据，记录写前备份和写后完整 verify；发布前保留旧固件及回退方法。
