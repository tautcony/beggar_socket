## Browser and real-ROM checks

- The headless real-ROM probe is retained as `web-client/scripts/run-gba-rom.mjs`, exposed through `npm run test:gba-rom -- --rom <path>`. It reuses the application compatibility helper and save bridge, preserves the 12,300-frame GOODBOY and 3,300-frame reload scenarios, and writes screenshots, saves, input hashes, and a JSON report to a new output directory. See `web-client/scripts/README-gba-rom.md` for reproducible commands, baseline failure mode, and interpretation limits.
- The retained CLI was exercised with the original GOODBOY fixture: `goodboy` completed 12,300 frames, produced two checkpoints, and exported the same 32 KiB SAV hash as the earlier probe (`29dc9e46afcc14ad8708e44c955f3f4c26423a3a6caf5b9b9d72cc16db90ce51`); `goodboy-reload` imported it exactly and completed 3,300 frames. Both fresh-core export/reimport checks passed. `--without-arm-compat` exited with status 1 after 1,590 completed frames, preserving SPSR `0x2f` and the original `Invalid user mode passed to selectBank` exception. Input hashes remained unchanged. Two concurrent 60-frame boot runs also passed without opening an HTTP/WebSocket listener.
- The user-provided `GOODBOY (Europe)_20250715-141645.sav` is 128 KiB while its ROM declares SRAM with a 32 KiB native window. The headless CLI imported it without changing the core allocation, reached a playable level after 3,300 frames with zero ERROR, and exported a 131,072-byte image with SHA-256 `61ffb806253907c0e3b0500aafe4c635d5d2b1feb046c2276892063a935b4f85`. Import prefix and exact-image checks passed; the 96 KiB suffix was byte-for-byte unchanged. Fresh-core export/reimport also matched. The source file remained unchanged. `/tmp/goodboy-save128-after/final.png` shows gameplay.
- CLI length checks also passed: a 3-byte SRAM raw input produced a normalized 32,768-byte output with all input bytes preserved (`importMatches` and `importPrefixMatches` true, `importExactMatch` false), and fresh-core export/reimport matched. The 128 KiB fixture reported all three import checks true and preserved the same SHA-256 above.

- The browser UI was exercised with a synthetic 32 KiB SRAM ROM/SAV pair. The core changed byte 0 from `0x5a` to `0x42`; export preserved the remaining bytes, close updated the in-memory RAM file, and export/reimport worked. A second incrementing ROM exported `0x5b`, then `0x5c` after reset, confirming reset used the latest checkpoint.
- A second browser round trip exported the changed 32 KiB save, reimported it as a real File, restarted the preview, and exported it again. Both outputs matched byte-for-byte, beginning with `0x42`, with no emulator errors.
- The browser conflict path used a differently named existing SAV filled with `0x5a`. Starting without it and writing `0x42` retained a recovery result, left the selected RAM file unchanged, and exported the new result. Successful export cleared the pending state and allowed another preview; cancellation kept recovery available. The default recovery filename used the ROM basename without its extension.
- Real user-supplied fixtures were tested against the installed `gbats` core with a software framebuffer, outside the browser UI. `宝可梦-绿宝石.gba` (`FLASH1M_V103`) loaded its 128 KiB paired SAV and reached the continue screen showing player `TC`, time 11:52, Pokédex 12, and 3 badges. Its input and exported save bytes matched. `粉色-GOODBOY (Europe).gba` (`SRAM_V111`) and its 32 KiB SAV ran for 180 frames without bridge errors and exported the expected capacity. These runs confirmed recognition and loading; neither fixture was saved in-game during this check.
- The reported GOODBOY language-menu failure was reproduced against `GOODBOY.rom` with a software framebuffer and empty SAV. After the language-selection input, `Bad I/O register read: 0x2` arrived at frame 438 as `LOG_WARN` (level 2). With logger severity handling fixed, the core continued through frame 780 and opening animation, with zero fatal errors and a valid 32 KiB save export. The source ROM and SAV were not modified. The warning is logged while remaining nonfatal; `LOG_ERROR` still opens the fatal error UI and retains the last valid checkpoint.
- A before/after core comparison confirmed the regression: before filtering severity, the same WARN at frame 438 paused execution by frame 439; after filtering, execution continued to frame 780. Stack-trace callbacks at level `-1` now log as debug and do not replace the original fatal error. Lifecycle regression tests cover WARN, INFO, DEBUG, negative trace levels, continued checkpoint/export, and an ERROR-level callback retaining the checkpoint.
- A later core trace found the separate SPSR mode-mask failure on `GOODBOY.rom`: frame 1590, FIQ `MOVS PC,LR` at `0x03006d88` (`0xe1b0f00e`) attempted to restore SPSR `0x2f`, which decodes to invalid mode `0x0f`. The preceding game code switched to FIQ; `MSR SPSR_c,r1` had lost M4 because gbats used `PRIV_MASK=0xcf`. The installed CPU then ran normally with only its instance mask changed to `0xdf`: the same input passed frame 4500 and reached English dialogue; a longer run reached 12,300 frames, entered a playable level, produced two 32 KiB checkpoints, and exported 32 KiB with no ERROR. These runs confirmed the cause and validation target before the application compatibility helper was added. No source ROM/SAV was modified. See the ARM7TDMI-S Technical Reference Manual §2.8.2/Table 2-2, linked above in `design.md`.
- After the application helper was installed, a fresh real `GOODBOY.rom` core imported the 32 KiB SAV from the long run. Immediate capture matched the imported bytes exactly. The game started past the language prompt, ran another 3,300 frames with zero ERROR, and exported a valid 32 KiB SAV again. The input SAV remained unchanged. The helper produced mask `0xdf` on the active core.
